# HIVE Windows Desktop Companion Implementation Plan

Date: 2026-07-14  
Design: `docs/superpowers/specs/2026-07-14-hive-desktop-companion-design.md`  
Target: Windows 10/11 x64, Electron

## Delivery rules

- Preserve the existing CLI/TUI and coding-session behavior; desktop code composes those modules.
- Work test-first for each task: add a focused failing test, capture the failure, implement the smallest behavior, then run focused and regression checks.
- Keep Electron out of the repository-local core.
- Do not persist plaintext credentials or copy tool output into threads.
- Do not make Git mutations without current status, reviewed scope, an action-bound confirmation, and a HEAD recheck.
- Do not stage, commit, push, or publish as an incidental implementation step.

## Task 1: Desktop core contracts, thread persistence, and turn context

Files:

- Create `src/desktop/types.ts`
- Create `src/desktop/thread-store.ts`
- Create `src/desktop/context.ts`
- Create `src/desktop/index.ts`
- Update `src/index.ts` only to append the desktop export
- Create `tests/desktop-core.test.mjs`
- Create the approved design and plan documents

Steps:

1. Add failing tests for create/list/load/save/archive, unsafe IDs, invalid schema shapes, 20,000-character limits, deterministic newest-first context, current-message retention, atomic temp cleanup, corrupt-snapshot preservation, and secret redaction.
2. Define schema-version-1 thread/message/run contracts and the desktop command, event, credential, store, run-manager, and guarded-Git interfaces. Credential commands expose metadata and write/test/remove operations only; they never expose resolver plaintext.
3. Implement `.hivemind/threads/<safe-id>/thread.json` persistence with exact raw-shape validation before sanitization, persisted-shape validation after sanitization, exclusive temporary writes, flush and rename, and typed corruption errors.
4. Implement local current-turn context and objective construction with no tool output or provider summarization. `run.start` carries repository/thread/current-message identity and options only; the runtime constructs the objective from persisted state.
5. Include canonical runtime-event forwarding, utility-worker lifecycle events, change-diff commands, bounded external open commands, and full-detail guarded Git preview/confirmation contracts.
6. Export the public core without changing existing exports.
7. Build, run the focused desktop test, and report RED and GREEN evidence.

Acceptance:

- Valid full thread records round-trip and archive without deletion.
- Invalid IDs/shapes and messages over 20,000 characters are rejected.
- A corrupt existing snapshot is byte-for-byte unchanged after a rejected save.
- Junction/symlink/reparse paths that resolve outside the repository are rejected before thread I/O.
- Concurrent creates for one ID have exactly one successful caller and leave no lock/temp artifacts.
- `save` rejects a missing thread instead of creating it.
- Persisted thread text contains no runner-detectable assignments, bearer values, or supported provider-token forms.
- Current-turn context always retains the required user message and drops older messages first within 20,000 characters.

Implemented service boundary details: run resume/cancel requests carry repository, thread, and coding-session identity; Git proposals carry the coding-session ID while worktree paths and HIVE branches are derived internally; discard has its own preview/confirmation; observed HEAD is generated by preview instead of trusted from renderer input.

## Task 2: Electron shell and hardened IPC boundary

Files to add or update:

- Electron main entry under `src/desktop/electron/main.ts`
- Context-isolated preload under `src/desktop/electron/preload.ts`
- IPC validation/router under `src/desktop/electron/ipc.ts`
- Desktop-specific TypeScript/build configuration and package scripts
- Focused main/preload contract tests

Steps:

1. Add failing tests for allowlisted command routing, malformed payload rejection, redacted errors, denied navigation/new windows, and renderer API shape.
2. Add Electron as a development/build dependency and configure a Windows x64 development launch without replacing existing CLI entry points.
3. Create one main window with `contextIsolation: true`, `nodeIntegration: false`, sandboxing where compatible, no remote content, denied arbitrary navigation, and a strict Content Security Policy.
4. Expose only typed request/subscription methods from preload. Do not expose Electron IPC primitives or Node APIs.
5. Persist non-sensitive window/recent-repository state under `app.getPath("userData")`.

Acceptance:

- Renderer code has no direct filesystem, process, credential, or raw IPC access.
- Unknown commands and malformed payloads fail before side effects.
- Existing CLI tests continue to pass.

## Task 3: Utility-process coding runtime bridge

Files to add or update:

- `src/desktop/electron/utility-entry.ts`
- `src/desktop/electron/run-manager.ts`
- Runtime event projection and lifecycle tests

Steps:

1. Add failing tests for start, event forwarding, cancellation, crash projection, resume, and duplicate-run prevention.
2. Start the existing coding runtime in an Electron utility process using structured-clone-safe inputs.
3. Resolve the selected repository and session in the main process; never accept an arbitrary renderer command line.
4. Forward normalized coding runtime events to the main process and persist each run reference update in its thread.
5. Implement cooperative cancellation and bounded process termination; map unexpected exits to failed/paused state based on the persisted session.

Acceptance:

- Long-running code work does not execute in or block the renderer/main event loops.
- A renderer reload or app restart can reconstruct run state from repository persistence.
- One submitted user turn cannot accidentally create duplicate coding sessions.

## Task 4: AppData credential vault and provider resolution

Files to add or update:

- `src/desktop/electron/credential-vault.ts`
- Main-process credential IPC handlers
- Credential vault tests using an injected `safeStorage` adapter

Steps:

1. Add failing tests for encrypt/store/resolve/remove, metadata-only listing, unavailable-encryption refusal, and redacted failures.
2. Store encrypted credential envelopes only under Electron userData/AppData.
3. Keep plaintext inside the main/utility process only for the active provider operation and never return it to the renderer.
4. Adapt provider startup through `CredentialResolver`; do not write credentials into repository config or process arguments.

Acceptance:

- No plaintext credential appears in repository files, AppData files, events, logs, or renderer state.
- The app refuses plaintext persistence when OS-backed encryption is unavailable.

## Task 5: Guarded Git service

Files to add or update:

- `src/desktop/git/guarded-git-service.ts`
- Main-process Git command handlers
- `tests/desktop-git.test.mjs`

Steps:

1. Add failing temporary-repository tests for status/diff, reviewed-path commits, stale HEAD, stale/incorrect confirmation, push target validation, dirty-baseline preservation, and blocked destructive/force operations.
2. Implement read-only status and diff inspection with structured results.
3. Issue short-lived, single-action confirmation tokens bound to the observed HEAD and proposed action.
4. Recheck repository root, HEAD, paths, remote, and branch immediately before commit/push.
5. Keep pull-request creation separate and explicit after push.

Acceptance:

- No mutation accepts raw Git argument arrays from the renderer.
- A changed HEAD or action details invalidate confirmation.
- Unselected pre-existing changes are not staged or committed.

## Task 6: Three-pane renderer

Files to add or update:

- Renderer entry and styles under `src/desktop/renderer`
- Left repository/thread pane components
- Center conversation/composer components
- Right run/activity/Git components
- Renderer tests

Steps:

1. Add failing tests for pane navigation, archived-thread visibility, composer validation, run association, activity updates, and confirmation dialogs.
2. Build the left repository/thread navigation, center durable conversation, and right session/activity/Git pane.
3. Keep raw command/tool output in the activity/session view and out of `ThreadMessage` persistence.
4. Add accessible keyboard navigation, visible focus, status announcements, scalable layout, and recoverable error presentation.

Acceptance:

- All three panes remain usable at the supported minimum window size.
- Submitted messages become durable only after main-process confirmation.
- Git and credential actions clearly show their security boundary.

## Task 7: Windows integration and recovery validation

Files to add or update:

- Release checklist documentation

Steps:

3. Verify paths containing spaces and non-ASCII repository names while thread IDs remain safe ASCII.
4. Run the full existing test suite and desktop-focused suite from a clean build.

Acceptance:

- Windows x64 smoke tests pass on a supported Windows 10/11 runner.
- CLI/TUI behavior and existing repository persistence remain compatible.
- No secret appears in captured logs or fixtures.
